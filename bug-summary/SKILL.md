# bug-summary

将一个问题的相关材料整理为适合长期沉淀的结构化问题文档，并额外生成一条可直接加入总 index 的摘要条目。

## 适用场景

在以下情况使用本 skill：
- 用户提供一个问题的复盘材料、分析记录、聊天摘录、日志摘要或半成品说明，希望整理成统一格式的问题文档。
- 用户希望输出结果后续可被其他 LLM 高效理解、引用、检索。
- 用户正在持续积累问题案例，需要单问题文档与总 index 摘要条目。

一次处理一个主问题文档。主问题文档内部可以包含多个阶段性子问题，但这些子问题必须服务于同一条问题主线。

## 核心目标

输出两部分内容：
1. **主输出**：主问题结构化文档（可包含多个子问题）
2. **辅输出**：可直接加入总 index 的摘要条目

## 工作流程

### 1. 先判断输入中有几个主问题

如果用户输入明显包含**两个及以上互不相关的主问题**（业务场景不同、排障主线不同），必须在生成任何文档之前先停下来，告诉用户本次只能处理一个主问题，并询问优先处理哪一个。

**不要擅自生成多份文档**——用户可能只想记录其中一个，也可能需要分别创建独立文件，自作主张两份都生成既绕过了用户的确认，也无法保证符合他们的实际归档意图。

判断两个问题”互不相关”的标准：它们的业务场景和排障主线明显不同，合并在一起阅读会让人感到割裂。

### 2. 识别核心语义锚点
在确认只处理一个主问题之后，优先识别以下信息：
- 业务场景
- 问题出现阶段
- 涉及对象 / 系统 / 模块 / 流程
- 核心现象

### 3. 缺核心锚点时，必须先追问
如果以下任一信息无法明确，先暂停，不要直接生成最终文档：
- 业务场景
- 主问题所处阶段
- 主问题对应的对象 / 模块 / 流程
- 主问题的核心现象

追问必须采用**结构化追问**，不要笼统地说”请补充更多信息”。
优先使用类似下面的问法：
- 这个问题对应的业务场景是什么？
- 这个问题出现在流程的哪一阶段？
- 涉及的系统、模块或对象是什么？
- 当前最明确的异常现象是什么？

拿到用户回复后，再继续生成最终文档。

### 4. 非核心信息缺失时，显式标注
对于严重级别、详细影响范围、验证结果、最终根因细节等非核心信息，如果输入中没有明确内容，可以在文档中写“待确认”，不要编造。

## 主输出格式

主输出采用 **YAML frontmatter + 固定 Markdown 结构**。文档粒度是“一个主问题”，而不是强行把每个阶段性子问题拆成独立文档。

### Frontmatter

```yaml
title:
business_scene:
stage:
status:
tags:
```

规则：
- `title`：使用强规则生成，优先采用“对象/模块 + 场景/阶段 + 异常结果”的形式。
- `business_scene`：必填。
- `stage`：必填。
- `status`：使用规范化状态值。
- `tags`：简洁关键词列表。

### 推荐状态值
- 待分析
- 分析中
- 待确认
- 已解决
- 部分解决

### 正文结构

```md
# 问题标题

## 问题背景

## 整体现象

## 子问题拆解
### 子问题 1：<标题>
#### 现象
#### 分析
##### 事实
##### 推断
##### 待确认
#### 解决方案

### 子问题 2：<标题>
#### 现象
#### 分析
##### 事实
##### 推断
##### 待确认
#### 解决方案

## 最终结论

## 元信息
```

## 各章节要求

### 问题标题
- 直接表达对象、场景/阶段、异常结果。
- 避免空泛标题。
- 便于后续检索与引用。

### 问题背景
这是硬性重点章节，必须明确写出：
- 业务场景
- 问题所处阶段
- 涉及对象 / 模块 / 流程

如果这些信息不足，先追问，再写文档。

### 整体现象
写清主问题层面的：
- 总体异常表现
- 影响对象 / 结果
- 关键证据（如有）

### 子问题拆解
**先判断是否真的需要拆子问题。** 子问题拆解适用于一个主问题中存在多个**独立的故障点**——每个故障点各自有独立的现象、独立的根因、独立的修复动作，读者需要分别理解和追踪它们。

以下情况**不应拆子问题**，而应在单一问题结构的分析章节中展开：
- 排查路径有多个步骤，但最终指向同一个根因
- 有"临时方案"和"长期方案"之分，但它们都在修复同一件事
- 不同阶段的分析是递进关系，而非并列关系

判断方法：问自己"如果把这两个'子问题'分别讲给别人，他们会觉得是在说两个不同的 bug，还是同一个 bug 的不同角度？"前者才值得拆，后者应整合。

当确实需要拆子问题时，每个子问题都应包含：
- 子问题标题
- 现象
- 分析
  - **事实**
  - **推断**
  - **待确认**
- 解决方案

子问题必须属于同一业务场景或同一条排障主线；不要把互不相关的问题塞进同一文档。

### 最终结论
汇总主问题层面的最终判断：
- 主问题最终结论
- 关键根因或关键转折点
- 最终处理结果 / 当前状态

### 元信息
保持简洁，仅保留：
- 当前状态
- 相关系统/模块
- 标签
- 输入材料概况

## LLM 易读要求

输出文档应满足：
- 章节固定
- 语义明确
- 优先短句
- 一段只表达一个意思
- 避免模糊代词
- 不把推断写成事实
- 缺失信息显式标注
- 使用中等细度，不写成长篇复盘

## 辅输出：总 index 摘要条目

每次生成主文档时，同时生成一条可直接加入总 index 的摘要条目。

建议格式：

```md
- **<问题标题>**
  - 场景：<业务场景>
  - 摘要：<一句话摘要>
  - 文档：`<问题文档路径>`
```

要求：
- 摘要足够简洁
- 必须明确业务场景
- 用于帮助人和 LLM 决定是否继续加载对应问题文档

## 输出顺序建议

1. 先输出主问题文档
2. 再输出一条 index 摘要条目

## 约束

- 一次处理一个主问题文档。主问题文档内部可以包含多个阶段性子问题，但这些子问题必须服务于同一条问题主线。
- 用户输入含多个互不相关的主问题时，先停下来询问优先处理哪一个，不要擅自生成多份文档。
- 子问题拆解只用于真正并列的独立故障点，不用于排查步骤、递进分析或临时/长期方案的区分。
- 不要把互不相关的多个主问题混在同一份问题文档中。
- 不要为了完整而编造信息。
- 缺核心锚点或问题边界不清时，必须暂停追问。
- 本 skill 不默认负责自动搭建完整目录系统或批量改写历史问题文档。
